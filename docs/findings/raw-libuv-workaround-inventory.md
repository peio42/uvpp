# Raw libuv workaround candidate inventory

- **Date:** 2026-11-11
- **Scope:** raw handles and requests, filesystem, DNS, work, random, threading and system wrappers, and shared raw helpers. Search included native calls, state guards, stop calls, retry loops, private fields, platform and version gates. High-level-only coroutine and owner helpers are excluded. This is a targeted source audit, not proof that every platform and libuv version has been exercised.
- **Evidence limit:** source and documented contracts are linked below; only the signal test was run in this audit. Existing findings distinguish their own earlier runtime evidence. A lack of a found upstream issue is not proof that none exists.

## Candidates retained

| uvpp location and intervention | Native behavior, assessment and evidence |
| --- | --- |
| `detail/poll_init.hpp:16–46`, `handles/poll.hpp:137–150`: directly unlink `handle_queue` and zero failed initialization storage | **Confirmed workaround for upstream defect**, not an ordinary ownership guard. Old Windows `uv_poll_init_socket` may register before `SO_PROTOCOL_INFOW` fails; a failed wrapper may otherwise leave a dangling registration. [Finding](uv-poll-init-windows-registration.md), [source analysis and version matrix](../design/raw-poll-init-rollback.md), [upstream fix PR #5379](https://github.com/libuv/libuv/pull/5379). Prior Windows fault injection is not an independent natural failure; no Windows runtime here. Private queue manipulation conflicts with the raw native-semantics invariant even when motivated by C++ lifetime; fixed-release boundary remains unverified. |
| `handles/signal.hpp:55–65,75–89`: use persistent native signal and stop before callback instead of native one-shot | **Workaround for suspected native rearm defect/ambiguous contract**; also changes actual signal handler reset timing. Linux native rearm returned success but was subsequently stopped. [Finding with source, contract and executed reproducer](upstream-signal-oneshot-rearm.md). No matching upstream issue found; propose asking upstream. |
| `handles/fs_poll.hpp:63–103,140–148`: reject changed active start with `UV_EBUSY`; reject zero/submillisecond interval | **Non-native restriction**, not shown to mask an upstream bug. Native active start returns success without replacing configuration; zero becomes 1 ms in [libuv source](https://github.com/libuv/libuv/blob/v1.51.0/src/fs-poll.c). Wrapper replaces callback for identical starts, another deliberate divergence. [Existing finding](raw-fs-poll-active-restart.md); [native documentation](https://docs.libuv.org/en/v1.x/fs_poll.html). Initial stat race is separate and not repaired by this guard: [upstream finding](upstream-fs-poll-initial-stat.md), [issue #4543](https://github.com/libuv/libuv/issues/4543). |
| `handles/poll.hpp:168–175,208–215`: stop on every negative status before terminal delivery | **Callback policy divergence**, no evidence of upstream defect. [Native contract](https://docs.libuv.org/en/v1.x/poll.html) specifies discontinuation for `UV_EBADF`, not every negative error. Releasing a C++ callback slot before delivery is an ownership policy, but adding native stop is observable; evaluate separately under raw semantics. No independent error-path runtime test performed. |
| `handles/fs_event.hpp:159–169`: stop on negative callback status | **Callback policy divergence**, not established as a libuv workaround. Native [fs-event contract](https://docs.libuv.org/en/v1.x/fs_event.html) reports errors; it does not generally promise all errors terminate the subscription. Windows repeated error callbacks have a separately reported [issue #5399](https://github.com/libuv/libuv/issues/5399); no evidence this code was introduced for that issue. No runtime verification here. |
| `handles/idle.hpp:50–56`, `check.hpp:50–56`, `prepare.hpp:50–56`: stop before restart | **Observable callback replacement policy**, not evidence of a defect. Native active starts do not necessarily replace callback; uvpp forces replacement and must account for user callable lifetime. Compare [libuv Unix loop watchers](https://github.com/libuv/libuv/blob/v1.x/src/unix/loop-watcher.c). |
| `handles/stream.hpp:116–133,138–161,357`: prevalidate accept/listen state and backlog | **Non-native restrictions**, not shown to target upstream bugs. In particular native listening/accept outcomes can differ from preemptive `EINVAL`/`EAGAIN`; type and lifetime checks protect wrapper invariants but each restriction is not necessarily required by C++ ownership. Compare [stream contract](https://docs.libuv.org/en/v1.x/stream.html) and [Unix stream source](https://github.com/libuv/libuv/blob/v1.x/src/unix/stream.c); platform-specific equivalence not established. |
| `handles/timer.hpp:83–89`: `again` rejects inactive timer | **Potential non-native restriction**, not a demonstrated upstream workaround. Compare [timer contract](https://docs.libuv.org/en/v1.x/timer.html) and [source](https://github.com/libuv/libuv/blob/v1.x/src/timer.c): native again uses stored repeat/callback, and may restart an inactive previously started repeating timer. No runtime test here. |

## Rejected candidates and limits

- Initialization, closing, and duplicate-close guards in `detail/initializable_handle.hpp`, `handles/handle.hpp`, TCP, UDP, process and watchers protect stable native storage or prevent calls after close; they are not evidence of a libuv defect. Their inconsistent observable statuses are covered by [existing close finding](raw-watcher-close-consistency.md).
- Request pending guards and callback rollback in `detail/stream_request.hpp`, `requests/{dns,random,work,request}.hpp` preserve a single request's storage and callback until native completion; cancellation is not completion. Filesystem's missing equivalent is an unrelated uvpp ownership issue documented in [request reuse](raw-fs-request-pending-reuse.md) and [closedir ownership](raw-closedir-cancellation-ownership.md).
- Stream and UDP read/receive terminal handling (`handles/stream.hpp:419`, `handles/udp.hpp:954`) retains buffer loans and callback slots through delivery and calls stop. It changes native callback policy, but no link to a native defect was identified; error-specific semantics should not be generalized from this audit.
- `handles/stream.hpp:417` checks out the current callback if a Windows zero-byte read error arrives without an allocation callback. This adapts delivery to a native callback sequence and preserves the callback loan; it does not suppress an error or establish a libuv defect. Windows runtime behavior was not verified here; compare the [stream callback contract](https://docs.libuv.org/en/v1.x/stream.html).
- Callback generation and loan handling in `core/callback.hpp`, `detail/raw_watcher.hpp`, stream and UDP keep moved/replaced C++ callables and borrowed buffers alive through reentrant delivery. No private libuv state is patched there.
- `handles/{fs_event,fs_poll,pipe}.hpp` path/name getter resize loops respond to native `UV_ENOBUFS` with the requested buffer size. These are output-buffer sizing retries, not retries of failed I/O to hide a libuv defect.
- Text NUL checks, buffer-size/count checks, duration conversion, and type checks in handles and filesystem code protect C string and C++ range representation. Some impose observable native restrictions; no evidence links them to upstream defects. `fs_poll` zero interval and stream backlog are called out above because native valid cases may be excluded.
- `core/version.hpp` and feature conditionals in handles, filesystem, DNS, random, threading and system code gate availability of API symbols and constants; no version-specific bug compensation was identified. Platform path conversions and UDP `recvmmsg` loan handling represent platform encoding and native buffer ownership, respectively.
- `handles/process.hpp:574–594` retains a started child on a failing spawn path for asynchronous lifetime/reaping; this is C++ lifetime management, not proof of a native defect. Platform behavior was not independently reproduced.
- Condition timed wait forwards its converted timeout; no clamp or retry masks the separately confirmed Linux overflow in [the timedwait finding](uv-cond-timedwait-overflow.md). A search found [#4803](https://github.com/libuv/libuv/issues/4803) about documentation, not the overflow; no matching overflow report was identified.
- DNS, filesystem, work, random, synchronous system helpers and network address/interface wrappers were inspected for retry and native-state interventions; no further defect-masking candidate was identified by this targeted search. This does not validate every operation's correctness or all platform branches.

## Unrelated existing uvpp findings

The pending filesystem request, cancelled `closedir`, and inconsistent duplicate close findings linked above are separate C++ lifecycle/consistency issues. They were not investigated further here.
